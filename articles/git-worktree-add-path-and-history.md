## 今日の問い

まだ作っていないフォルダに `cd` で移動しようとすると、エラーになります。ところが、`git worktree add` にまだ存在しないフォルダを指定すると、その場所にプロジェクトのファイルまで現れます。Gitは何を作ったのでしょうか。

`cd` に渡すパスは「移動先」です。`git worktree add` に渡すパスは「これから作業用のファイルを展開する場所」です。なぜそんなコマンドがあるのかは、編集中のファイルを残したまま、同じプロジェクトの別の版を開きたい場面を考えると見えてきます。

## ブランチを二つ作っても、開けるファイルは一つ

たとえば、読書メモの `topics.txt` に項目を書き足している途中で、「追加する前の版で、別の修正を試したい」とします。

Gitでは、ファイルの状態を記録した一区切りを**コミット**、その履歴を保管する場所を**リポジトリ**と呼びます。**ブランチ**は、作業を進めるたびに新しいコミットを指すようになる名前です。ブランチを二つ作っても、エディターで開ける `topics.txt` が自動的に二つになるわけではありません。実際にファイルを開いて編集する場所が**作業ツリー（worktree）**です。

作業ツリーが一つなら、変更をいったん退避してブランチを切り替え、あとで戻して作業を再開できます。もう一つの方法は、リポジトリを別の場所に複製すること。Gitではこれを**クローン**と呼びます。二つのフォルダを同時に開ける一方、片方で新しく作ったコミットをもう片方でも使うには、履歴を取り込む手間が生まれます。

## 2015年、履歴を共有したまま作業場所を増やせるようになった

2015年7月、Git 2.5で `git worktree` コマンドが登場しました。当時のGitHubのリリース解説には、片方で時間のかかるテストを走らせながら、もう片方で開発を続ける例があります。テストが終わるまでは、そのフォルダのファイルをテスト開始時の状態に保ちたい。でも、そのために二つのリポジトリの履歴を同期し続けるのは面倒です。

ここで分けると都合がいいのは、**手元のファイル**と**いま開いているブランチ**です。一方、過去のコミットはどちらからも同じものを読めます。`git worktree` は、この境目で作業場所を分けます。追加したフォルダの中をのぞくと、Gitの管理情報を示す `.git` が小さなファイルになっています。そこに、この作業ツリー用の管理情報の場所が書かれています。

## 書き足した一行は、どちらのフォルダに現れるか

次の例では、`notes` フォルダで `topics.txt` に `Git` と書いた状態をすでにコミットしてあります。その後に `worktree` と一行書き足し、ファイルを保存しました。この二行目はまだコミットしていません。

この状態で、`notes` の中から次を実行します。新しいブランチ名とフォルダ名を区別しやすいように、それぞれ違う名前を付けます。

```bash
git worktree add -b review ../notes-review HEAD
```

- `-b review` は、新しいブランチに付ける名前を指定します。
- `../notes-review` は、新しく作る作業場所です。`..` は一つ上の階層を表すので、`notes` と横並びになります。
- `HEAD` は、いま開いているコミットを指します。ここでは新しいブランチの出発点です。

`cat` で二つのファイルの中身を表示すると、違いが見えます。以下はGit 2.55.0で実行して確認した結果です。

```console
$ cat topics.txt
Git
worktree

$ cat ../notes-review/topics.txt
Git
```

もしGitが元のフォルダを丸ごとコピーしたなら、どちらにも `worktree` の行があるはずです。実際に新しい場所に展開されたのは、`HEAD` が指すコミットに記録されていた一行だけでした。元のフォルダには手元で編集した二行が残っています。これなら、書きかけの行を片付けずに、隣のフォルダで別の修正を試せます。

冒頭の問いに戻ると、存在しないパスを指定できるのは、**そのパスが、新しい作業ツリーの作成先だから**です。あとから「どのフォルダで、どのブランチを開いていたっけ？」と迷ったら、`git worktree list` でパスとブランチの対応を一緒に確認できます。
